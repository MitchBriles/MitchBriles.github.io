The suggested fixes below are sketches written from reading the code. Only the RISC-V stack realignment fix has been built and tested.

The four denormal_fpenv bugs rest on this LangRef text: "If the input mode is preservesign, or positivezero, a floating-point operation must treat any input denormal value as zero." Output flushing is optional ("It is not mandated that flushing to zero occurs"). So a non-flushed result is fine, but a result computed from a non-flushed input is wrong. Alive2 has modelled input flushing as mandatory since AliveToolkit/alive2#1350. That is why the 40 denormal-only tests in regehr-bugs/ pass on older builds and fail now. Each of the 40 verifies once denormal_fpenv is removed.

[SelectionDAG] frem nsz by 2^n drops the sign of a zero result

bugs/frem-nsz-signed-zero/

define float @f(float %a) {
  %r = frem nsz float %a, 1.000000e+00
  ret float %r
}
fround.s  fa5, fa0, rtz
fsub.s    fa0, fa0, fa5
# no fsgnj.s

Expected result. For x = -2^65, fmod(x, 1.0) is -0.0, because the result takes the dividend's sign. nsz does not permit anything else here. LangRef says: "the sign bit of 0.0 or -0.0 input operands can be non-deterministically flipped". Neither operand is a zero, and frem defines no exception for its result.

Actual result. x - trunc(x) evaluates to +0.0. Without nsz, llc appends fsgnj.s fa0, fa5, fa0 and the result is correct.

Runtime

repro.ll prints 80000000 under llubi and 00000000 from the compiled program.

repro.ll

@x = dso_local global float 0xC014000000000000
@fmt = private unnamed_addr constant [6 x i8] c"%08x\0A\00"

declare i32 @printf(ptr, ...)

define dso_local i32 @main() {
  %a = load volatile float, ptr @x
  %r = frem nsz float %a, 1.000000e+00
  %bits = bitcast float %r to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %bits)
  ret i32 0
}
Cause

DAGCombiner::visitFREM computes NeedsCopySign = !DAG.canIgnoreSignBitOfZero(SDValue(N, 0)) && .... The SDValue overload SelectionDAG::canIgnoreSignBitOfZero returns true as soon as Op has nsz. That treats nsz on the defining node as a license over its result. The SDUse overload, which checks the user's flags, is correct.

Scope. The bug is target-independent. x86-64 (with SSE4.1) and AArch64 drop their sign fix-up the same way. It needs a legal FTRUNC and a power-of-two divisor.

Suggested fix
  • Minimal: in visitFREM, decide NeedsCopySign from the users only, not from the frem's own flags: 
    bool NeedsCopySign =
    !DAG.cannotBeOrderedNegativeFP(N0) &&
    !all_of(N->uses(), [&](SDUse &U) { return DAG.canIgnoreSignBitOfZero(U); });
  • Principled: remove the nsz early return from the SDValue overload of canIgnoreSignBitOfZero. Since #180906, nsz on a node grants nothing about its result.
    • The one caller that legitimately relies on it is the sitofp/uitofp fold. LangRef makes a zero result's sign non-deterministic there under nsz, so that caller should check the flag itself.
    • The other callers need auditing: the fadd/fsub zero folds and X/sqrt(X).

[CodeGen] Two uses of freeze undef observe different values

bugs/freeze-undef-split/

define i32 @f() {
  %w = freeze i32 undef
  %p = call i32 @llvm.ctpop.i32(i32 %w)
  %r = call i32 @llvm.smin.i32(i32 %w, i32 %p)
  ret i32 %r
}
cpopw   a0, a0         # overwrites w with ctpop(w)
sext.w  a1, a0         # second use of w reads ctpop(w)
min     a0, a1, a0     # a0 = min(ctpop(w), ctpop(w))

Expected result. freeze returns one fixed value, so the result is smin(w, ctpop(w)). That is never 32: if w >= 0 then ctpop(w) <= 31, and if w < 0 the result is w.

Actual result. The code returns ctpop of whatever a0 held on entry, which is 32 when the low 32 bits of a0 are all ones.

Runtime

repro.ll passes -1 in a0 through an unused argument. The compiled program prints 32. llubi prints smin(w, ctpop(w)) for whatever value it picks for w, so any value but 32.

repro.ll

@fmt = private unnamed_addr constant [4 x i8] c"%d\0A\00"

declare i32 @printf(ptr, ...)

define i32 @f(i32 %unused) noinline {
  %w = freeze i32 undef
  %p = call i32 @llvm.ctpop.i32(i32 %w)
  %r = call i32 @llvm.smin.i32(i32 %w, i32 %p)
  ret i32 %r
}

define i32 @main() {
  %r = call i32 @f(i32 -1)
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %r)
  ret i32 0
}
Cause

The MIR after isel is correct: one IMPLICIT_DEF and two reads of a single vreg. Then:

  1. detect-dead-lanes marks both reads undef.
  2. processimpdefs deletes the IMPLICIT_DEF.
  3. With no live range tying the two reads together, the scheduler hoists CPOPW, and the greedy allocator assigns its def to the register the second read uses.

#222832 fixed this pattern only for tied operands. That fix is in the tested build, and the bug still reproduces.

The underlying reason is that SelectionDAGISel::Select_FREEZE lowers FREEZE to a plain COPY. Its comment says: "We don't have FREEZE pseudo-instruction in MachineInstr-level now". After isel, a frozen undef is indistinguishable from a plain one, so machine passes may treat each read independently.

Suggested fix
  • Simplest: in DAGCombiner::visitFREEZE, fold freeze(undef) and freeze(poison) to a zero constant of the same type. Any fixed value is a legal choice, and zero is free on RISC-V (x0). No IMPLICIT_DEF then reaches MIR from a freeze.
  • General: add a FREEZE machine pseudo, as that TODO anticipates. This also covers values that only become undef after legalization.

Keeping every multi-reader IMPLICIT_DEF alive in DetectDeadLanes/ProcessImplicitDefs would also work, but it would pessimize ordinary undef, which can't be told apart after isel.

[SelectionDAG] copysign(x, fptrunc(y)) -> copysign(x, y) with a multi-use fptrunc gives a NaN with two observed signs

bugs/copysign-fpround-nan-sign/

define half @f(half %a, float %b, ptr %p) {
  %c = fptrunc float %b to half
  store half %c, ptr %p
  %t = call half @llvm.copysign.f16(half %a, half %c)
  ret half %t
}
fmv.x.w   a1, fa1
srli      a1, a1, 31      # copysign takes the sign from %b ...
...
fcvt.h.s  fa5, fa1        # ... but the stored %c comes from fcvt, which gives +qNaN
fsh       fa5, 0(a0)

Expected result. %c is a single value. If fptrunc yields a NaN, LangRef lets its sign be non-deterministic, but whatever sign it picks, sign(%t) must equal the sign of the stored %c.

Actual result. For a negative-NaN %b, the store writes +qNaN (0x7e00) while %t is negative.

Runtime

repro.ll prints the stored %c and the returned copysign(+0, %c).

  • Compiled: 7e00 8000. The stored value is positive, but the copysign result is -0.
  • llubi: fe00 8000, which is consistent.

repro.ll

@b = dso_local global float 0xFFF8000000000000
@out = dso_local global half 0xH0000
@fmt = private unnamed_addr constant [11 x i8] c"%04x %04x\0A\00"

declare i32 @printf(ptr, ...)
declare half @llvm.copysign.f16(half, half)

define half @f(half %a, float %b) noinline {
  %c = fptrunc float %b to half
  store half %c, ptr @out
  %t = call half @llvm.copysign.f16(half %a, half %c)
  ret half %t
}

define i32 @main() {
  %b = load volatile float, ptr @b
  %t = call half @f(half 0xH0000, float %b)
  %c = load half, ptr @out
  %cb = bitcast half %c to i16
  %tb = bitcast half %t to i16
  %c32 = zext i16 %cb to i32
  %t32 = zext i16 %tb to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %c32, i32 %t32)
  ret i32 0
}
Cause

DAGCombiner::visitFCOPYSIGN performs this fold unconditionally (CanCombineFCOPYSIGN_EXTEND_ROUND). This lets the copysign and the other users of the cast see different NaN signs. The same fold also rewrites fp_extend; I have not tested that form.

Suggested fix

Guard the fold:

if (CanCombineFCOPYSIGN_EXTEND_ROUND(N) &&
    (N1.hasOneUse() || DAG.isKnownNeverNaN(N1.getOperand(0))))
  return DAG.getNode(ISD::FCOPYSIGN, DL, VT, N0, N1.getOperand(0));
  • With one use, only the copysign observes the cast's sign. A NaN's sign is already non-deterministic, so taking y's sign is a legal choice.
  • If y is never NaN, the cast preserves its sign, so extra uses are fine.

[SelectionDAG] Lowering of memset.i32 sign-extends length FIXED

bugs/memset-i32-len-sext/

define void @f(ptr %p) {
  call void @llvm.memset.p0.i32(ptr %p, i8 0, i32 -2147483648, i1 false)
  ret void
}
lui   a2, 524288      # a2 = 0xFFFFFFFF80000000 on RV64
li    a1, 0
call  memset

Spec status. LangRef says only that len is "an integer argument specifying the number of bytes to fill". It does not state a signedness, and it lists no UB for large or negative lengths. The only UB clause is "if <len> is not a well-defined value", and "well defined" is a LangRef term meaning no undef bits and not poison. So i32 0x80000000 is a fully defined operand. Every other in-tree interpretation reads it as unsigned:

  • SelectionDAG::getMemset's inline path: ConstantSize->getZExtValue().
  • LowerMemIntrinsics (memset expanded as a loop): the known-size path uses Len->getZExtValue(), and the runtime loop in insertLoopExpansion is bounded by CreateICmpULT.
  • llubi: LengthInt.getZExtValue(), and it reports "length overflows uint64_t".
  • Alive2: treats len as unsigned.

The libcall path is the only one that differs, and it doesn't choose a signed reading either. It leaves the upper bits unspecified. The same IR therefore fills 2^31 bytes when LLVM expands memset itself, and about 2^64 bytes when it calls libc. If lengths of 2^31 or more are meant to be UB, LangRef should say so.

Expected result (unsigned, as above). 0x80000000 means 2^31 bytes, and libc memset takes a 64-bit size_t, so the caller should pass 0x0000000080000000.

Actual result. memset receives 0xFFFFFFFF80000000 (about 2^64 bytes) and writes far past the destination. This affects every i32 length of 2^31 or more, constant or runtime. For a runtime length, the i32 register is passed through unchanged. The RV64 psABI keeps 32-bit values sign-extended in registers, so the upper half is a copy of bit 31.

Impact. Probably low. Frontends emit size_t-typed lengths (i64 on 64-bit targets), so this needs an i32 memset of 2 GiB or more on a 64-bit target.

Runtime

repro.ll mallocs 2^31+16 bytes, memsets exactly 2^31 of them through an i32 length, and reads the last byte back. This is in bounds and must print 1.

  • Compiled: overruns the buffer. Under a 4 GiB memory cap it is killed.
  • Control (the same program with the length explicitly zexted to i64): prints 1 under the same cap.
  • llubi cannot model a 2 GiB allocation, so it is not a witness here.

repro.ll

@len = dso_local global i32 -2147483648
@fmt = private unnamed_addr constant [4 x i8] c"%d\0A\00"

declare ptr @malloc(i64)
declare i32 @printf(ptr, ...)
declare void @llvm.memset.p0.i32(ptr, i8, i32, i1)

define i32 @main() {
  %p = call ptr @malloc(i64 2147483664)
  %n = load volatile i32, ptr @len
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %n)
  call void @llvm.memset.p0.i32(ptr %p, i8 1, i32 %n, i1 false)
  %last = getelementptr i8, ptr %p, i64 2147483647
  %v = load i8, ptr %last
  %v32 = zext i8 %v to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %v32)
  ret i32 0
}
Cause
  • SelectionDAGBuilder passes the i32 length to SelectionDAG::getMemset unchanged.
  • getMemset builds the libcall argument as Args.emplace_back(Size, DL.getIntPtrType(Ctx)), i.e. an i32 node for an i64 parameter, with neither IsZExt nor IsSExt set.
  • LowerCallTo therefore extends it with ANY_EXTEND, leaving the upper 32 bits unspecified.
  • The inline path in the same function already treats the length as unsigned (ConstantSize->getZExtValue()).

Scope. memcpy and memmove are lowered the same way; I've checked their assembly but haven't run them. On x86-64 and AArch64 the upper bits are also left to the incoming register (for example x86 kill: def $edx ... def $rdx). They are only correct when those bits happen to be zero, which their ABIs don't guarantee; this is inferred, not run.

Suggested fix

SelectionDAG::getMemcpy, getMemmove and getMemset all build the libcall argument as Args.emplace_back(Size, ...getIntPtrType(...)). Zero-extend the size first in each:

Size = getZExtOrTrunc(Size, dl, TLI->getPointerTy(getDataLayout()));

Marking the argument entry IsZExt would do the same thing. If lengths of 2^31 or more are instead meant to be UB, the fix is one sentence in LangRef's memset/memcpy/memmove sections, and the code can stay.

[DAGCombiner] freeze of a sub-byte load loses the truncation (AssertZext after freeze is unsound for non-byte widths)

bugs/freeze-subbyte-load-assertzext/

define i32 @f(ptr %p) {
  %v = load i1, ptr %p
  %w = freeze i1 %v
  %z = zext i1 %w to i32
  ret i32 %z
}
lbu  a0, 0(a0)       # no andi a0, a0, 1
ret

Expected result. Since #180739 (2026-03-10), LangRef says a non-byte-sized load "behaves like a byte-sized load followed by a trunc nuw". If the byte holds 0x20, %v is poison, freeze makes it 0 or 1, and %z is 0 or 1.

Actual result. The raw byte is returned.

Runtime

repro.ll stores i8 32 into the global and then runs the function above on it. The compiled program prints 32; llubi prints 0.

repro.ll

@G = dso_local global i8 32
@fmt = private unnamed_addr constant [4 x i8] c"%d\0A\00"

declare i32 @printf(ptr, ...)

define i32 @f() noinline {
  %v = load i1, ptr @G
  %w = freeze i1 %v
  %z = zext i1 %w to i32
  ret i32 %z
}

define i32 @main() {
  %r = call i32 @f()
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %r)
  ret i32 0
}
Cause
  • The DAG rewrites zero_extend(freeze(load i1)) into AssertZext(freeze(zextload i64 from i1), i1).
  • reduceLoadWidth looks through the freeze and re-wraps it with AssertZext ExtVT (if (FreezeNode) { ... if (ExtType == ISD::ZEXTLOAD) ... AssertZext ...).
  • For a byte-multiple ExtVT the assertion is true. For i1/i2, the zextload is a plain byte load that keeps the upper bits. The assertion is therefore false once memory holds anything except 0/1, and the and 1 is dropped.
  • Related: #218454 ("freeze(load) can never be dropped").

The fuzzer also hit this with i2 loads, and on 2026-10-08 with i3 through inttoptr (an implicit zext). load i3; freeze; zext compiles to a bare lbu on RISC-V, movzbl on x86-64 and ldrb on AArch64. It affects every non-byte width, not just i1/i2, and every target I tried. Without the freeze the same bare byte load is correct, because an out-of-range byte makes the load poison.

Suggested fix

In reduceLoadWidth, only look through a freeze when the narrowed type is byte-sized:

if (N0.getOpcode() == ISD::FREEZE) {
  if (!ExtVT.isByteSized())
    return SDValue();
  FreezeNode = N0;
  N0 = N0.getOperand(0);
}

Dropping only the AssertZext should not be enough. A zextload from i1 is selected as a plain byte load, so the frozen value would still carry the upper bits, and nothing masks them. Before #189317 the freeze blocked this fold entirely. I have not checked whether the output before #189317 was correct.

[RISCV] Stack realignment to 2^32 bytes emits andi sp, sp, 0 FIXED

bugs/riscv-stack-realign-4g/ (from regehr-bugs/6b2ed310)

define void @f() {
  %1 = alloca i1, align 4294967296
  %2 = load i1, ptr %1, align 4294967296
  store i1 false, ptr %1, align 4294967296
  ret void
}
addi   s0, sp, 496
bseti  a0, zero, 33
addi   a0, a0, -496
sub    sp, sp, a0
andi   sp, sp, 0         # sp = 0
bseti  a0, zero, 32
add    a0, a0, sp
sb     zero, 0(a0)       # store to address 2^32

Expected result. 2^32 is the largest alignment LLVM allows (Value::MaxAlignmentExponent), so the IR is valid. sp should be rounded down to a multiple of 2^32, as x86-64 (andq $-4294967296, %rsp) and AArch64 (and sp, x9, #0xffffffff00000000) do.

Actual result. sp is set to 0, and the store goes to address 2^32.

Runtime

repro.ll calls @f and then prints ok. The frame needs about 8 GiB of stack, so qemu's default 8 MiB stack segfaults with or without the bug. Give it a 12 GiB stack, as a byte count (-s 12G is misparsed as 128 KiB):

qemu-riscv64 -s 12884901888 ./repro_single
  • Buggy (andi sp, sp, 0): SIGSEGV (exit 139).
  • With the fix below: prints ok.
  • llubi prints ok.

The stack is reserved but barely touched, so this needs little real memory.

repro.ll

@fmt = private unnamed_addr constant [4 x i8] c"ok\0A\00"

declare i32 @printf(ptr, ...)

define void @f() noinline {
  %a = alloca i8, align 4294967296
  store volatile i8 0, ptr %a
  ret void
}

define i32 @main() {
  call void @f()
  call i32 (ptr, ...) @printf(ptr @fmt)
  ret i32 0
}

backend-tv. It cannot detect this bug. On regehr/arm-tv it flags the buggy and the fixed code alike, because its stack model is too small for any realignment of 1024 or more (TOOL_BUGS.md #9). The fuzzer only reported this case because of that false alarm; the miscompile itself was found by reading the asm. On arm-tv-fuzzing the case gets Stack frame too large. Use the qemu run above.

Cause

RISCVFrameLowering::emitPrologue (RISCVFrameLowering.cpp:1238):

if (isInt<12>(-(int)MaxAlignment.value())) {
  BuildMI(MBB, MBBI, DL, TII->get(RISCV::ANDI), SPReg)
      .addReg(SPReg)
      .addImm(-(int)MaxAlignment.value())

MaxAlignment.value() is a uint64_t, and (int)4294967296 is 0. So isInt<12>(0) holds and the ANDI gets immediate 0. Smaller alignments are unaffected: 2^31 becomes INT_MIN, which fails isInt<12>, so it takes the correct SRLI/SLLI path.

Scope. RISC-V only, and only for an alignment of exactly 2^32. Impact is low.

Suggested fix

Tested: with it, llc emits srli a0, sp, 32; slli sp, a0, 32 and the qemu run prints ok. Do the negation in 64 bits:

int64_t NegAlign = -(int64_t)MaxAlignment.value();
if (isInt<12>(NegAlign)) {
  BuildMI(MBB, MBBI, DL, TII->get(RISCV::ANDI), SPReg)
      .addReg(SPReg)
      .addImm(NegAlign)

[SelectionDAG] getNegatedExpression uses nsz on fadd/fsub to fold away an fneg, flipping the sign of a zero result

bugs/fneg-nsz/ (from regehr-bugs/2743204f and regehr-bugs/a7131871)

define float @f(float %x) {
  %s = fsub nsz float %x, 4.000000e+00
  %n = fneg float %s
  ret float %n
}

define float @g(float %x) {
  %s = fadd nsz float %x, 4.000000e+00
  %n = fneg float %s
  ret float %n
}
f:  fli.s   fa5, 4.0
    fsub.s  fa0, fa5, fa0        # 4.0 - x
g:  fli.s   fa5, 4.0
    fneg.s  fa5, fa5
    fsub.s  fa0, fa5, fa0        # -4.0 - x

Expected result. For f(4.0), 4.0 - 4.0 is +0.0 and fneg makes it -0.0. nsz does not permit anything else. LangRef (since #180906) says only "the sign bit of 0.0 or -0.0 input operands can be non-deterministically flipped", and neither input is a zero. g(-4.0) is the same: -(-4.0 + 4.0) is -0.0.

Actual result. 4.0 - x and -4.0 - x both give +0.0. Without nsz, llc emits fsub.s followed by fneg.s, which is correct.

Runtime

repro.ll prints f(4.0) and g(-4.0). The compiled program prints 00000000 twice; llubi prints 80000000 twice.

repro.ll

@x = dso_local global float 4.000000e+00
@fmt = private unnamed_addr constant [6 x i8] c"%08x\0A\00"

declare i32 @printf(ptr, ...)

define float @f(float %x) noinline {
  %s = fsub nsz float %x, 4.000000e+00
  %n = fneg float %s
  ret float %n
}

define float @g(float %x) noinline {
  %s = fadd nsz float %x, 4.000000e+00
  %n = fneg float %s
  ret float %n
}

define i32 @main() {
  %x = load volatile float, ptr @x
  %r = call float @f(float %x)
  %b = bitcast float %r to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %b)
  %nx = fneg float %x
  %r2 = call float @g(float %nx)
  %b2 = bitcast float %r2 to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %b2)
  ret i32 0
}
Cause

TargetLowering::getNegatedExpression (TargetLowering.cpp):

  • The FSUB case folds fneg (fsub X, Y) -> fsub Y, X. It is guarded by if (!Flags.hasNoSignedZeros()) break; with the comment "We can't turn -(A-B) into B-A when we honor signed zeros".
  • The FADD case folds fneg (fadd X, Y) -> fsub (fneg X), Y behind the same check.

In both, Flags belongs to the fadd/fsub, so the nsz on the arithmetic node is read as a license over the sign of its result. That was the old nsz meaning. The rewrites differ from the original only when the result is a zero coming from nonzero inputs (X == Y for fsub, X == -Y for fadd), and there the input-only nsz grants nothing. This is the same stale reading as the frem nsz bug above.

One sub-fold is still correct: fneg (fsub 0, Y) -> Y, because nsz may flip the zero input to -0.0, and -(-0.0 - Y) is Y.

Scope. Target-independent. x86-64 (subss) and AArch64 (fsub s0, s1, s0) emit the same reversed subtraction. regehr-bugs/a7131871, -(-x + -y) with nsz on the fadd, becomes fadd.s fa0, fa0, fa1. That test also has denormal_fpenv, but it fails the same way without it.

Suggested fix

Keep the fsub 0, Y sub-fold. Stop using the fadd/fsub's own nsz for the rest:

  • Minimal: gate the swap and the FADD rewrite on DAG.getTarget().Options.NoSignedZerosFPMath.
  • Better: have callers pass down whether the negated value's users ignore the sign of zero, the SDUse form of canIgnoreSignBitOfZero, and require that instead.

This is the same audit that the frem nsz bug calls for.

[SelectionDAG] FP constant folding ignores denormal_fpenv input flushing

bugs/dag-constfold-denormal/ (33 tests in regehr-bugs/)

define float @f() #0 {
  %r = fadd float f0x80800000, f0x00400000
  ret float %r
}

attributes #0 = { denormal_fpenv(ieee|positivezero) }
lui      a0, 525312       # 0x80400000
fmv.w.x  fa0, a0

Expected result. Under positivezero input mode, the denormal input 0x00400000 must be read as +0.0. So the result is -2^-126 + 0 = -2^-126, which is 0x80800000. The IR constant folder agrees: opt -passes=instsimplify gives ret float f0x80800000, because ConstantFolding.cpp (flushDenormalConstant) honors the mode.

Actual result. 0x80400000, the unflushed IEEE sum.

Runtime

The compiled repro.ll prints 80400000. llubi prints 80800000 with its default seed. Some seeds give 80400000, because llubi's input flushing is itself random; see TOOL_BUGS.md #8.

repro.ll

@x = dso_local global float 0.0
@fmt = private unnamed_addr constant [6 x i8] c"%08x\0A\00"

declare i32 @printf(ptr, ...)

define float @f(float %unused) #0 noinline {
  %r = fadd float f0x80800000, f0x00400000
  ret float %r
}

define i32 @main() {
  %x = load volatile float, ptr @x
  %r = call float @f(float %x)
  %b = bitcast float %r to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %b)
  ret i32 0
}

attributes #0 = { denormal_fpenv(ieee|positivezero) }
Cause

SelectionDAG::foldConstantFPMath (SelectionDAG.cpp:8229) folds with plain APFloat arithmetic and never looks at getDenormalMode(VT). The FP path of FoldSetCC (SelectionDAG.cpp:2698) has the same problem. The 12 fcmp tests compare two different denormal constants. For example, regehr-bugs/2a0d5cad has fcmp une double f0x0008100000000000, f0x0008000000000000, which folds to true. Both operands flush to zero, so it must be false.

Scope.

  • fadd of the constants above: x86-64 and AArch64 give 0x80400000, the same wrong result. AMDGPU and NVPTX give 0x80800000.
  • fmul: x86-64 and AArch64 are wrong.
  • fcmp une: RISC-V, x86-64 and AArch64 fold to true; AMDGPU folds to false.

On x86-64 and AArch64 this is a miscompile even for users who do set DAZ/FZ as the attribute requires. The folded constant differs from what the instruction would have computed at run time.

Suggested fix

In foldConstantFPMath and the FP branch of FoldSetCC, read DenormalMode Mode = getDenormalMode(VT), then:

  • bail out if Mode.Input is Dynamic;
  • otherwise flush denormal operands to ±0.0 as Mode.Input says before folding, as flushDenormalConstant does in the IR folder.

Output flushing is optional, so the folded result can stay as computed.

[InstSimplify][DAGCombiner] x - 0.0 -> x and x + -0.0 -> x ignore denormal_fpenv input flushing

bugs/identity-fold-denormal/ (4 tests in regehr-bugs/)

define float @f(float %x) #0 {
  %r = fsub float %x, 0.000000e+00
  ret float %r
}

attributes #0 = { denormal_fpenv(preservesign) }
ret                     # returns x unchanged

Expected result. Under a flushing input mode, fsub must read a denormal %x as zero, so a denormal %x gives ±0.0, never %x. LangRef adds that "the input may need to be converted to 0 as if by @llvm.canonicalize" when an instruction doesn't flush.

Actual result. %x is returned unchanged.

Runtime

repro.ll passes the denormal 0x00000001. The compiled program prints 00000001; llubi prints 00000000.

On RISC-V this can't be separated from the next bug, since a real fsub.s wouldn't flush either. The fold is visible on targets that do honor the attribute:

  • AMDGPU (gfx900) emits only s_setpc_b64. The control function fsub float %x, %y emits v_sub_f32, which flushes under the function's mode.
  • NVPTX emits a plain ld.param/st.param copy.
  • At IR level, opt -passes=instsimplify rewrites the function to ret float %x.

repro.ll

@x = dso_local global float 0x36A0000000000000
@fmt = private unnamed_addr constant [6 x i8] c"%08x\0A\00"

declare i32 @printf(ptr, ...)

define float @f(float %x) #0 noinline {
  %r = fsub float %x, 0.000000e+00
  ret float %r
}

define i32 @main() {
  %x = load volatile float, ptr @x
  %r = call float @f(float %x)
  %b = bitcast float %r to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %b)
  ret i32 0
}

attributes #0 = { denormal_fpenv(preservesign) }
Cause

None of these folds checks the input denormal mode:

  • InstSimplify: simplifyFAddInst "fadd X, -0 ==> X" (InstructionSimplify.cpp:6038) and simplifyFSubInst "fsub X, +0 ==> X" (:6104). The nsz variants just below them (fadd X, +0, fsub X, -0) have the same problem.
  • DAGCombiner: visitFADD "N0 + -0.0 --> N0" (DAGCombiner.cpp:19447) and visitFSUB "(fsub A, 0) -> A" (:19661).

Twenty lines further down, visitFSUB already guards fsub -0.0, X -> fneg X with if (DenormMode == DenormalMode::getIEEE()) and the comment "We cannot replace an FSUB(+-0.0,X) with FNEG(X) when denormals are flushed to zero". That guard is why regehr-bugs/15c5a597 keeps its fsub.s.

A related IR fold is already known to be wrong. InstCombine turns fsub -0.0, X into fneg X (InstCombineAddSub.cpp:3295) under the comment "FIXME This matcher does not respect FTZ or DAZ yet: fsub -0.0, Denorm ==> +-0; fneg Denorm ==> -Denorm". The DAG's version of the same fold is guarded (see above), but the IR version is not.

Scope. All targets, and IR. Other operand-returning folds, such as fmul X, 1.0 and fdiv X, 1.0, likely have the same problem; I have not tested them.

Suggested fix

Fold to X only when the input mode for the type is IEEE:

  • IR: F->getDenormalMode(Ty->getScalarType()->getFltSemantics()).Input == DenormalMode::IEEE.
  • DAG: DAG.getDenormalMode(VT).Input == DenormalMode::IEEE.

Otherwise fold to llvm.canonicalize(X) / ISD::FCANONICALIZE where it is legal, or leave the operation alone.

[RISCV] denormal_fpenv input flushing modes are silently ignored

bugs/riscv-denormal-input-mode/ (3 tests in regehr-bugs/)

define float @f(float %x, float %y) #0 {
  %r = fadd float %x, %y
  ret float %r
}

attributes #0 = { denormal_fpenv(preservesign) }
fadd.s  fa0, fa0, fa1

Expected result. Per LangRef the operation "must treat any input denormal value as zero", so 0x00000001 + 0.0 is +0.0.

Actual result. RISC-V fadd.s always handles subnormals as IEEE requires. The F/D extensions have no flush-to-zero or denormals-are-zero control; fcsr holds only frm and fflags. So no user or platform setup can give the promised mode, and llc does not canonicalize inputs.

Runtime

repro.ll passes 0x00000001 and 0.0. The compiled program prints 00000001; llubi prints 00000000.

repro.ll

@x = dso_local global float 0x36A0000000000000
@fmt = private unnamed_addr constant [6 x i8] c"%08x\0A\00"

declare i32 @printf(ptr, ...)

define float @f(float %x, float %y) #0 noinline {
  %r = fadd float %x, %y
  ret float %r
}

define i32 @main() {
  %x = load volatile float, ptr @x
  %r = call float @f(float %x, float 0.0)
  %b = bitcast float %r to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %b)
  ret i32 0
}

attributes #0 = { denormal_fpenv(preservesign) }

Spec status. This is a documented limitation rather than a clear miscompile. LangRef says "Currently this attribute is respected by the AMDGPU and NVPTX backends" and "no attempt is made to diagnose unsupported uses". It is also told the user is "expected to set the floating point mode appropriately before function entry", which is impossible on RISC-V. On x86-64 (MXCSR.DAZ) and AArch64 (FPCR.FZ) the user can set it, so the same code is correct there. The mandatory-flush wording for inputs sits badly with a backend that can do nothing to honor it.

Scope. RISC-V, for every FP operation in a function whose input mode is not ieee. The three regehr-bugs/ tests are fsub -0.0, x, with and without a select, for float and double.

backend-tv catches these three only because two other bugs cancel out:

  • The lifter copies denormal_fpenv onto the lifted function (TOOL_BUGS.md #7), so the lifted fsub.s is modelled as flushing. On its own, that would hide the bug: all three verify with --optimize-tgt=O0.
  • backend-tv's default -O3 then runs the InstCombine fsub -0.0, X -> fneg X fold from the previous section on the lifted IR. That fold drops the flush again, and the mismatch reappears.

For the same reason, the fadd in reduced.ll is not flagged by backend-tv at all.

Suggested fix

Either direction would resolve it:

  • Honor it: when the input mode is not IEEE, lower FP operations with explicit input canonicalization. That means an fclass-based select to ±0.0 for each operand. It is correct but slow, which is acceptable for a mode that is rare on RISC-V.
  • Or document it: state in LangRef that on targets without hardware denormal control, the input mode is not honored for emitted instructions and only restricts what the optimizer may assume. Then emit a warning when llc sees such a mode on RISC-V.

This probably belongs as a Discourse question before an issue.

[InstCombine][DAGCombiner] store i1 undef is deleted, but a non-byte-sized store must zero the rest of the byte

bugs/store-subbyte-undef/ (from the 2026-10-08 run, seed min-max/smin_undef_i32)

define void @f(ptr %p) {
  store i1 undef, ptr %p
  ret void
}
ret                     # no store

Expected result. Since #180739 (2026-03-10), LangRef says a non-byte-sized store "behaves like a zext followed by a byte-sized store". zext i1 undef to i8 is 0 or 1, so after the store the byte must be 0 or 1, whatever it held before.

Actual result. The store is deleted, so the byte keeps its old value.

Runtime

repro.ll starts with @g = i8 4, calls @f(@g), and prints @g. The compiled program prints 4; llubi prints 0 or 1, depending on --seed.

repro.ll

@g = dso_local global i8 4
@fmt = private unnamed_addr constant [4 x i8] c"%d\0A\00"

declare i32 @printf(ptr, ...)

define void @f(ptr %p) noinline {
  store i1 undef, ptr %p
  ret void
}

define i32 @main() {
  call void @f(ptr @g)
  %v = load i8, ptr @g
  %w = zext i8 %v to i32
  call i32 (ptr, ...) @printf(ptr @fmt, i32 %w)
  ret i32 0
}
Cause

Both folds treat any undef stored value as a no-op:

  • DAGCombiner::visitSTORE, "Turn 'store undef, Ptr' -> nothing.": if (Value.isUndef() && ST->isUnindexed() && !ST->isVolatile()) return Chain;.
  • InstCombinerImpl::visitStoreInst, "store undef, Ptr -> noop": if (isa<UndefValue>(Val)) return eraseInstFromFunction(SI);. Its FIXME already notes another problem (#52930: the store might overwrite poison), but not this one.

That was correct when the extra bits of a sub-byte store were unspecified. Under the zext rule, only a fully poison value may be dropped: zext(poison) is poison, but zext(undef) has known-zero high bits.

Scope. Every target (x86-64 and AArch64 also emit a bare ret), and the IR pipeline (opt -O2 deletes it too). Any non-byte width (i1, i2, i17, …) is affected. Byte-sized store iN undef is fine.

Suggested fix

In both folds, require the stored type to be byte-sized or the value to be poison:

// DAGCombiner::visitSTORE
if (Value.isUndef() && ST->isUnindexed() && !ST->isVolatile() &&
    (Value.getOpcode() == ISD::POISON ||
     ST->getMemoryVT().isByteSized()))
  return Chain;
// InstCombinerImpl::visitStoreInst
if (isa<PoisonValue>(Val) ||
    (isa<UndefValue>(Val) && DL.typeSizeEqualsStoreSize(Val->getType())))
  return eraseInstFromFunction(SI);

Otherwise, store zero.
