Alive2 (AliveToolkit/alive2)

1. noundef makes struct padding non-poison, giving false memory mismatches

Status. Present on upstream master and regehr/arm-tv. Fixed on arm-tv-fuzzing (8409f4ef, with the two lit tests below); not yet sent upstream.

Description. A noundef call return or !noundef load becomes Assume(WellDefined). Every later read of that value then sets all non-poison bits, the padding element's included, with expr::mkInt(-1, np). This happens at two sites: State::eval and State::getAndAddPoisonUB (ir/state.cpp). An aggregate store therefore writes padding as a defined 0x00. LangRef says the opposite on both points: well-definedness "doesn't consider the padding of an aggregate", and a store fills padding with undef. When the target leaves the padding untouched, Alive2 reports "Mismatch in memory". All 118 padded-struct false alarms in the 5-hour run have this shape (a noundef aggregate that is then stored). The two I re-ran with the fix now verify.

Repro. tools/padding-noundef.srctgt.ll, run with alive-tv -tgt-is-asm:

define void @src(ptr %p, i16 %a, i16 %b) {
  %r = call noundef { i16, i1 } @llvm.sadd.with.overflow.i16(i16 %a, i16 %b)
  store { i16, i1 } %r, ptr %p, align 2
  ret void
}
define void @tgt(ptr %p, i16 %a, i16 %b) {   ; stores both fields, never byte 3
  %r = call { i16, i1 } @llvm.sadd.with.overflow.i16(i16 %a, i16 %b)
  %v = extractvalue { i16, i1 } %r, 0
  %o = extractvalue { i16, i1 } %r, 1
  store i16 %v, ptr %p, align 2
  %q = getelementptr i8, ptr %p, i64 2
  %o8 = zext i1 %o to i8
  store i8 %o8, ptr %q, align 1
  ret void
}

Unpatched: Mismatch in pointer(non-local, block_id=1, offset=3), with source #x00 and target #x01. Byte 3 is padding.

Suggested fix. This is what I implemented locally. Add a helper shaped like State::freeze that forces non-poison bits everywhere except padding. It recurses through non-vector aggregates and rebuilds them with aggregateVals, which puts poison back in the padding slots. Use it at both sites.

  • The full alive-tv suite shows no regressions (its one failure is pre-existing, confirmed by an A/B build).
  • Two lit tests were added in tests/alive-tv/asm/padding-noundef-store{,-fail}.srctgt.ll.

2. Fast-math flags on sitofp/uitofp are not supported

Status. Present on both branches. On arm-tv the instruction is refused as "Unsupported instruction". Upstream master passes the flags to FpConversionOp, whose constructor has assert(fmath.isNone()) for everything except fpext/fptrunc (ir/instr.cpp). So an assertion build aborts, and a release build silently ignores the flags. The upstream behaviour is from reading the code; I haven't run it.

Description. LangRef allows fast-math flags on {s,u}itofp since #198470 (2026-05). It also gives nsz specific meaning there: "If the input value is 0, the sign bit of the result is non-deterministic." The fuzzer hit this 8 times across nnan, ninf and nsz, on scalars and vectors.

Repro. tools/itofp-fmf.srctgt.ll:

define double @src(i32 %a) {
  %r = uitofp nnan i32 %a to double
  ret double %r
}
define double @tgt(i32 %a) {
  %r = uitofp i32 %a to double
  ret double %r
}

Result: ERROR: Unsupported instruction: %r = uitofp nnan i32 %a to double.

Suggested fix. Model the flags in FpConversionOp::toSMT for SIntToFP and UIntToFP:

  • nnan: a no-op, since integer-to-FP conversion never produces a NaN.
  • ninf: poison when the result is ±Inf. This can happen when narrowing, e.g. i32 → half.
  • nsz: when the input is 0, pass the result through any_fp_zero.
  • arcp, contract, reassoc, afn: no effect on a single correctly rounded conversion.

Then drop the assertion and the llvm2alive refusal.

Until then, llvm-ir-mutator --alive2-safe strips fast-math flags from int-to-FP conversions (70f9aa0).

6. Asm mode reports a valid load of an align 1 global as UB

Status. Present on arm-tv eb9f9335. I have not found the cause. I only checked arm-tv; master also has -tgt-is-asm, but I haven't run this there. This is the cause of regehr-bugs/c5b79f85, the only Source is more defined than target result among the 44.

Description.

  • backend-tv runs -O3 over the lifted IR before checking it.
  • For regehr-bugs/c5b79f85 (tools/lifted-o3-speculated-load.ll), the source is store 0, %p; select %c, @g0, %p; load.
  • -O3 hoists load @g0 above the select. That is legal: LLVM treats a non-extern_weak global as dereferenceable for its type's size, and plain alive-tv verifies the same source/target pair.
  • In asm mode (-tgt-is-asm, which backend-tv uses), Alive2 reports the hoisted load as UB. In the counterexample %p points to @g0's own block, which is alive, 4 bytes, and in bounds.
  • With --optimize-tgt=O0, c5b79f85 verifies.

The false alarm needs every one of these. Changing any single one makes it verify:

  • @g0 has align 1; align 4 verifies.
  • The target loads it as i32; i8 verifies.
  • There is an align 4 access through the pointer argument; align 1 verifies.
  • @g0 is not constant.

Repro. tools/asm-mode-align1-global.srctgt.ll, run with alive-tv -tgt-is-asm:

@g0 = global i32 0, align 1

define ptr @src(ptr %p) {
  %x = load i32, ptr %p, align 4
  ret ptr @g0
}

define ptr @tgt(ptr %p) {
  %x = load i32, ptr %p, align 4
  %g = load i32, ptr @g0, align 1
  ret ptr @g0
}
ERROR: Source is more defined than target
  ptr %p = pointer(non-local, block_id=1, offset=0) / Address=#x0000000000000004
  Target: i32 %g = UB triggered!
  (block 1: size 4, align 1, alive, address 0x4)

Without -tgt-is-asm it verifies.

Suggested fix (direction). The access through %p appears to constrain the target's view of @g0's block in a way that the align 1 access then fails. Start from the asm-mode branches in ir/memory.cpp: computeAliasing, which in asm mode uses the block id only when p.isInbounds(true) is implied, mayalias, and the alignment checks on access. Until it's fixed, fuzz.py could re-run Source is more defined results with --optimize-tgt=O0 and discard the ones that then verify.

**A second shape (2026-10-08 run, seed memset-inline/memset_zero_8).** A memset through an argument, followed by an align 4 store to a global, gives a false target UB in asm mode only. tools/asm-mode-memset-align.srctgt.ll:

@G = global i32 1
define void @src(ptr %a) {
  call void @llvm.memset.p0.i64(ptr %a, i8 0, i64 4, i1 false)
  store i32 2, ptr @G, align 4
  ret void
}
define void @tgt(ptr %a) {
  store i32 0, ptr %a, align 1
  store i32 2, ptr @G, align 4
  ret void
}
  • alive-tv -tgt-is-asm reports Source is more defined than target; plain alive-tv verifies.
  • If the source also uses store i32 0, ptr %a, align 1 instead of the memset, it verifies.
  • If @G has align 1, it verifies.

Like the first shape, this points at how asm mode relates the alignment of an argument-block access to a global's block.

10. A pointer load/store round trip is not treated as identity when memory holds mixed bytes

Status. Present on arm-tv-fuzzing (2986fdff), in both IR and asm mode. Found by the 2026-10-08 run (seed addimm-mulimm/add_mul_combine_reject_g1).

Description.

  • In the source, a function loads a ptr from a global, stores to an unrelated global, then stores the loaded ptr back.
  • The target drops the round trip: llc removes the load/store pair as a no-op, as EarlyCSE does in IR. With a freeze in between, llc keeps a plain ld/sd copy instead.
  • Alive2 lets the global's initial bytes be a mix of pointer bytes and integer bytes. In its model, load ptr of such bytes yields one well-formed pointer, so storing it back changes the bytes. The target leaves them untouched, so Alive2 reports Mismatch in memory.
  • The machine code preserves the memory bits exactly, and LangRef says backend passes do not see byte-level semantics ("backend passes do not see the byte type and do not preserve its bit-level semantics"). So llc's output is correct.
  • The disagreement is with Alive2's mid-end view, in which load ptr is not a byte copy. LangRef's new byte type exists for that case.

Without the intervening store, both forms verify.

The same model also bites when such a loaded pointer is passed to a call (call @f(ptr %LGV), where %LGV = load ptr, ptr @G and @G = global ptr poison). Alive2 then fails to match the two calls' inputs and models them independently, which gives Value mismatch or Mismatch in memory after the call. 3 of the 2026-10-08 candidates were this, and each verifies with ptr null as the argument.

Repro. tools/ptr-roundtrip.srctgt.ll (plain alive-tv, also -tgt-is-asm) and tools/ptr-roundtrip.ll (backend-tv):

@G = global ptr null
@H = global i32 1

define void @src() {
  %p = load ptr, ptr @G, align 8
  store i32 0, ptr @H, align 4
  store ptr %p, ptr @G, align 8
  ret void
}

define void @tgt() {
  store i32 0, ptr @H, align 4
  ret void
}
ERROR: Mismatch in memory
Mismatch in pointer(non-local, block_id=1, offset=0)
Source value: pointer(non-local, block_id=0, offset=1153343991949819904), byte offset=0
Target value: pointer(non-local, block_id=1, offset=360305566670651384), byte offset=0

Suggested fix (direction). For the asm target, compare memory as bits rather than as typed bytes. Alternatively, when the source stores back a value it loaded from the same location, treat that as a byte copy. It is only a false alarm in asm mode, so a narrow change there is enough for backend-tv. Whether the IR-mode verdict is right is a separate semantics question.

backend-tv (regehr/alive2, branch arm-tv)

3. A local's address passed to a call gives a false "Source is more defined than target"

Status. Present. This is likely the dominant false alarm. Every function did not return case I inspected (addi_fold_crash, fsw_stack, caller_no_realign2048) passes a local's address to a callee. I haven't classified all 438 such results from the 8-hour run.

Description.

  • The source passes the callee a pointer to its own 4-byte local block.
  • The lifted target passes phy-ptr(sp+4), a pointer into the lifter's single frame-sized stack block, which also holds the saved ra.
  • Alive2 can't match the two calls' inputs, so it models them independently. In the counterexample the target's callee "triggered UB" while the source's callee "did not return", which makes the source more defined.

Passing a non-local pointer to the same callee verifies.

Repro. tools/escaped-local-call.ll:

declare void @ext(ptr)
define void @f() {
  %a = alloca i32
  call void @ext(ptr %a)
  ret void
}
ERROR: Source is more defined than target
  Source: void = function did not return!
  Target: Function @ext triggered UB

Suggested fix (direction). Make an escaped stack object look the same to the callee on both sides:

  • either give each escaped stack slot its own block in the lifted target, using the frame layout from llc's MachineFrameInfo;
  • or, in asm mode, relate the source alloca block to the corresponding sub-range of the target stack block when matching call inputs.

triage.py sorts this signature (did not return in the source plus callee UB in the target) into escaped-local. In the 2026-10-08 run that was 231 of 339 unsound results, plus 79 did-not-return.

A related form: the target's memory before a call is more defined than the source's, but not identical. For example, the source stores i2 poison and the target stores the masked byte (andi 3; sb). Alive2 again models the callees independently, and the memory after the call mismatches. A 15-line repro of this is in the ohm run (b026c5e7…, seed calling-conv-sext-zext/anyint32_arg_to_uint8_ret). Matching call inputs up to refinement, rather than equality, would fix both forms.

4. A local's address that escapes by value is compared by address

Status. Present. This caused about 10 Value mismatch / Mismatch in memory results in the 8-hour run, and 4 in the 2026-10-08 run.

It also fires when the address is returned (ret ptr %A) or stored to a global (store ptr %A, ptr @G), not only for out-of-bounds GEPs. triage.py calls this class local-address.

Description. The source places its alloca at the start of the local address space (0x8000000000000000). The lifted target has the same object at sp+12, which is offset 0x3fc into its stack block. In bounds, the two pointers are matched by provenance and verify. Once a GEP leaves the object's 4 bytes, they are compared as raw addresses and differ. An alloca's address is unspecified, so the target's placement is a legal choice. The false alarm needs the alloca to be really allocated, which a store forces; without the store it verifies.

Repro. tools/oob-local-pointer.ll:

define ptr @f(i32 %v) {
  %a = alloca i32
  store i32 %v, ptr %a
  %g = getelementptr i8, ptr %a, i64 512
  ret ptr %g
}
ERROR: Value mismatch
  Source value: pointer(local, block_id=0, offset=512) / Address=#x8000000000000200
  Target value: phy-ptr(addr=...)                      / Address=#x80000000000005fc

Suggested fix (direction). In asm mode, let each source local block's address be chosen to match the target's stack-slot address, rather than fixing it at the local base. Alternatively, treat the address of a pointer based on a source local block as unconstrained once it leaves the block. This shares a root cause with #3, a mismatch between the source's per-alloca blocks and the target's single stack block, so one frame-layout mapping could fix both.

7. The lifter copies the source's attributes onto the lifted function

Status. Present on eb9f9335 and arm-tv-fuzzing. This one gives false negatives: backend-tv says "correct" for code that computes the wrong value.

Description. mc2llvm.cpp:797 runs liftedFn->copyAttributesFrom(srcFn);, so the lifted function inherits the source's denormal_fpenv. Alive2 then models each lifted FP operation as flushing denormal inputs, as LangRef requires. The RISC-V instructions never flush: there is no FTZ/DAZ control. The lifted IR therefore claims semantics the assembly doesn't have, and the source and target agree only because both are modelled wrongly.

It also interacts with LLVM. regehr-bugs/15c5a597, 2bad131b and 70b8547d fail only because backend-tv's -O3 over the lifted IR runs InstCombine's fsub -0.0, X -> fneg X, which ignores the attribute (a known FIXME). That fold removes the modelled flush. With --optimize-tgt=O0 all three verify, even though the RISC-V code is wrong (REPORTS.md, "RISC-V ignores the input mode").

Repro. tools/lifted-denormal-attr.ll:

define float @f(float %x, float %y) #0 {
  %r = fadd float %x, %y
  ret float %r
}

attributes #0 = { denormal_fpenv(preservesign) }

backend-tv reports Transformation seems to be correct!. llc emits a bare fadd.s. Running that same function in bugs/riscv-denormal-input-mode/repro.ll with x = 0x00000001 and y = 0.0 prints 00000001 under qemu, where LangRef requires 00000000.

Suggested fix. After copyAttributesFrom, give the lifted function the mode the hardware actually implements. The code right after line 797 already does this for memory effects ("The source function's memory effects don't describe the lifted code"). For RISC-V:

liftedFn->removeFnAttr(llvm::Attribute::DenormalFPEnv);

The default is then ieee|ieee. A backend with a real flush mode (AArch64 FPCR.FZ) would need that mode modelled explicitly instead. Stripping the attribute also removes the dependence on the InstCombine FIXME.

Parameter attributes too (false alarm, 2026-10-08 run). copyAttributesFrom also copies parameter attributes, such as nofpclass(nan).

  • In the lifted IR a NaN argument is then poison.
  • In the source it is only poison until a freeze. The register itself just holds the NaN bits.
  • After -O3 folds the lifted code using the copied attribute, the target stores poison where the source stores a frozen value, which Alive2 reports as Mismatch in memory.
  • Without the attribute it verifies.

tools/lifted-nofpclass.ll:

define i1 @f(float nofpclass(nan) %a, ptr %G) {
  %w = freeze float %a
  store float %w, ptr %G, align 4
  %C = fcmp ord float %w, 0.000000e+00
  ret i1 %C
}

Fix: drop the poison-generating parameter and return attributes from the lifted function (nofpclass, range, nonnull, align, dereferenceable, noundef), keeping only those that describe the ABI (signext, zeroext).

9. The stack-size check ignores realignment padding, turning big realigned frames into false alarms

Status. Present on regehr/arm-tv. Fixed on arm-tv-fuzzing (2986fdff), which uses the fix below: over-aligned frames now get the clean Stack frame too large error. This also means backend-tv can no longer see the 2^32 realignment bug at all; it was only ever found by reading the asm (REPORTS.md).

Description. The lifter models the stack as a single 1024-byte region (stackBytes in mc2llvm.h). checkSupport (mc2llvm.cpp:979-981, 1207) totals the source alloca sizes and rejects the function with ERROR: Stack frame too large, consider increasing stackBytes once that total reaches 1024. It never counts the padding that realignment adds. A small over-aligned alloca therefore passes the check, but llc realigns sp by up to the alignment. The target's stores then land outside the modelled region, and Alive2 reports Source is more defined than target, even though the code is correct.

Measured with a 1-byte alloca plus a load and a store (the shape of bugs/riscv-stack-realign-4g/reduced.ll):

  • align 16 to 512: verifies.
  • align 1024 and above: false alarm.

This includes the 2^32 case with the LLVM fix applied, where the asm (srli/slli) is correct and runs correctly under qemu. For comparison, a plain [1100 x i8] alloca gets the clean "too large" error.

Repro. tools/overaligned-alloca.ll:

define void @f() {
  %1 = alloca i1, align 1024
  %2 = load i1, ptr %1, align 1024
  store i1 false, ptr %1, align 1024
  ret void
}
ERROR: Source is more defined than target

Suggested fix. In the alloca loop, also count the worst-case realignment for over-aligned allocas, so these functions get the existing clean error:

if (allocSize)
  totalAllocas += allocSize->getFixedValue();
if (ai->getAlign().value() > 16)
  totalAllocas += ai->getAlign().value();

16 is the RISC-V/AArch64 stack alignment. Supporting such frames for real would need the stack region sized from the actual frame, MachineFrameInfo's stack size plus max alignment, rather than a constant.

11. shadowcallstack functions are reported as target UB

Status. Present on arm-tv-fuzzing. It accounts for the unconfirmed shadowcallstack hit from the 8-hour run, one candidate in the 2026-10-08 run, and several of the seeds that fail unmutated (shadowcallstack/f3..f5, shadow-stack-frame-opts/*).

Description. With shadowcallstack, llc saves ra to the shadow stack through gp: addi gp, gp, 8; sd ra, -8(gp). The lifter treats gp as an arbitrary incoming value, so the store goes through a pointer to no known block, and Alive2 calls the whole target UB.

Repro. tools/shadowcallstack.ll:

declare void @foo()
define void @f() shadowcallstack {
  call void @foo()
  ret void
}

Result: ERROR: Source is more defined than target.

Suggested fix. Model gp on entry as a pointer into a dedicated shadow-stack block, the way sp points into the stack block, when the function has shadowcallstack. Or reject such functions as unsupported. Until then, mkseeds.py could drop seeds with shadowcallstack.

llubi (llvm/llvm-project, llvm/tools/llubi)

8. llubi flushes denormal inputs at random

Suggested GitHub issue title: **[llubi] Denormal input flushing under denormal_fpenv is non-deterministic, but LangRef makes it mandatory**

Status. Present at 5c1c22673ce6.

Description. handleDenormal (llvm/tools/llubi/lib/Interpreter.cpp:159) does this:

if (IsInput) {
  // Non-deterministically choose between flushing or preserving the
  // denormal value.
  if (Ctx.getRandomBool())
    return Val;
}

Inputs are flushed at random, and outputs always. LangRef has it the other way round:

  • For inputs: "a floating-point operation must treat any input denormal value as zero".
  • For outputs: "It is not mandated that flushing to zero occurs".

So llubi can report a value that no conforming execution produces, and it can never produce a legal unflushed output. This matters when llubi is the oracle: for bugs/dag-constfold-denormal, the answer depends on --seed.

Repro. tools/llubi-denormal-inputs.ll computes fadd f0x80800000, f0x00400000 under denormal_fpenv(ieee|positivezero):

for s in $(seq 1 12); do llubi --seed=$s llubi-denormal-inputs.ll; done

Seeds 3, 4, 7, 8, 9 and 11 print 80400000. The only correct value is 80800000, which the other six seeds print.

Suggested fix. Swap the non-determinism: always flush inputs when the input mode is preservesign/positivezero, and choose at random whether to flush a denormal output.

Checked and not counted as tool bugs

  • **ret float poison NaN-box assertion.** This was an LLVM RISC-V miscompile, fixed upstream by #225567. backend-tv's assertion was correct.
  • **Recursive calls reported as function did not return.** This is a modelling limit in Alive2. llvm-ir-mutator --alive2-safe now breaks recursion, and seeds with recursion are skipped.
  • **SMT Error: smt tactic failed ... (incomplete quantifiers).** This is the solver giving up, not a wrong verdict.
  • **musttail calls returning i128 give "Target's return value is more undefined"** (14 hits in the 8-hour run). This was a mutator artifact: its recursion breaker skipped musttail calls, and FuzzMutate rewires the callee of musttail-indirect-args seeds into a self-call. Fixed in llvm-ir-mutator ec0eb91.
  • **The 40 denormal_fpenv failures in regehr-bugs/.** These are correct verdicts: LLVM bugs in REPORTS.md, exposed by alive2#1350 making input flushing mandatory. The only tool interference is #7, and the llubi seed dependence in #8.

Not yet confirmed

  • SMT Error: bit-vector size must be greater than zero: 50 hits in the 5-hour run and 57 in the 2026-10-08 run. The ohm representative (an fptosi half to i1) verifies locally with the same build, and so do minimal fptosi/fptoui to i1 cases. It may depend on load or timing on ohm.
  • ERROR: Precondition is always false (2 hits): a memcmp of 4 GiB, which is UB for every input. Not a tool bug.
