[RFC] Respecting freeze semantics in backends

Hi.

LangRef says a freeze of poison or undef “returns an arbitrary, but fixed, value.” The middle-end uses this fact for some transformations and, for the most part, honors this rule.

The problem

On the other hand, backends do not generally respect freeze semantics. The SelectionDAG, FastISel, and GlobalISel selectors on AArch64, AMDGPU, RISC-V, and X86 all unconditionally lower freeze/ISD::FREEZE/G_FREEZE to a COPY. If the input to the freeze is undef or poison, what’s left is a COPY of IMPLICIT_DEF, which represents an undef value. ProcessImplicitDefs and the register coalescer then treat the COPY as undefined, and different uses can read different registers. The consequence is a long history of miscompiles including, but not limited to, these open issues:

#58321 #60429 #144780

Solutions

Contributors have been aware of this issue since at least 2022, and a few ideas have been suggested over the years. Here are a few:

  1. Pick some value (say, 0) for freeze(poison) in ISel — Very safe, but unacceptable performance regressions in some cases.
  2. Add a generic FREEZE MI opcode — Perhaps best for handling undefined lanes created after ISel, but probably the most work to implement without regressions.
  3. Select freeze(poison) as INIT_UNDEF — I’ve been experimenting with this one. INIT_UNDEF is an existing generic pseudo that is a non-rematerializable definition. With some MachineCSE support, PeepholeOptimizer support, and a couple of other tweaks, this seems to do the trick with little to no performance regressions. If people are interested in this approach, let me know, and I can link to a patch.

Regardless of which fix people prefer, I’m happy to code and submit it myself. Please let me know your thoughts!
